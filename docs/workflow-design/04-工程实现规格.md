# 04 工程实现规格

> 本文件定义**这套系统怎么跑起来**：编排与状态机、存储与缓存、模型网关与提示词规范、
> 成本模型、可观测性、安全与合规、部署形态。仍然是设计，不含代码。

---

## 1. 编排与状态机

### 1.1 为什么必须用工作流引擎
一次生产跨越 6–20 分钟、多个模型、人工等待、可能失败重试。用"一个脚本从头跑到尾"的后果：
失败要全量重跑、成本不可控、人工闸门无处等待、无法观测。

**选型**：Temporal（首要）/ Prefect / 自研队列 + 状态表。
判据：**持久化执行 + 可等待外部事件（人工审批）+ 重试语义 + 可回放**。

### 1.2 状态机

```
created
  └─(L1)→ topic_ready ──G1──▶ gate1_pending ──approved──▶ researched (L2)
                        │                         └─rejected─▶ created(换角度) | discarded
                        └─timeout/expired─▶ discarded
researched ─(L3 outline)→ scripted ──G2──▶ gate2_pending ──approved──▶ storyboarded (L4)
                                              │                 └─rejected─▶ scripted(最多3)
                                              └─fail_checks─▶ scripted(自动重写，不打扰人)
storyboarded ─(L4 audio/shot)→ rendered (L5) ─▶ qa_passed (L6)
          ▲                         │ fail    │
          └────── route_back ◀───────┴─────────┴──▶ gate3_pending ──approved──▶ scheduled → published → measured
                                                        └─discard─▶ discarded
任意状态 --budget_exceeded / 3×error--> failed（保留全部产物，可人工续跑）
```

**关键语义**
- 每个状态转移都产生 `stage_history` 条目（attempt、耗时、成本）。
- 状态转移只能通过事件（`StageCompleted` / `GateDecided` / `TimerFired` / `BudgetExceeded`）。
- 任何状态可**从产物重入**：给定 `artifact_id` 即可从该点续跑（幂等）。
- 人工等待有 TTL；超时按闸门策略处理（见 03）。

### 1.3 重试与熔断

| 场景 | 策略 |
|---|---|
| 模型 5xx / 超时 | 指数退避重试 3 次（1s/4s/16s），换备用供应商 1 次 |
| schema 校验失败 | 带错误信息让模型修复 2 次，仍失败 → 阶段失败 |
| QA 不通过 | 定向回流，同类问题最多 3 轮 |
| 单 run 成本超 80% 预算 | 降级（关生成片段、减少变体），并发告警 |
| 单 run 超 100% 预算 / 超时 | 终止为 `failed`，保留产物 |
| 全局每日预算耗尽 | 队列暂停，新 run 进 `created` 排队 |

## 2. 存储与缓存

| 类型 | 选型 | 说明 |
|---|---|---|
| 产物（JSON/媒体） | S3 兼容（MinIO 可自建） | 内容寻址，只追加，生命周期策略（原始素材 90 天转冷） |
| 元数据 | Postgres | run/stage/artifact/成本/闸门/发布记录 |
| 缓存 | 对象存储 + Redis 索引 | `cache_key → artifact_id` 映射 |
| 队列 | Redis Streams / SQS / Temporal 内置 | 三类分池：LLM、CPU 渲染、GPU 生成 |
| 配置 | 配置中心（版本化 YAML/JSON） | 阈值、平台规范、模型路由、预算 |

**缓存三层**
1. **阶段级**：`cache_key` 命中直接复用 `artifact_id`（选题/研究/脚本都极适合）。
2. **镜头级**：`shot_key` 命中直接复用渲染片段，最终只 concat（这是"改一个字不重渲全片"的实现）。
3. **资产级**：相同 prompt+seed+style 的生成图/片段复用资产。

缓存必须支持**强制失效**（改阈值/改 prompt 版本/改 style → 版本号变化自动失效）。

## 3. 模型网关与路由

### 3.1 网关能力（所有模型调用的唯一入口）
统一能力接口 `chat / embed / image / video / tts / asr`；提供：多供应商路由、key 池与限流、
自动重试与降级、结构化输出校验、token 与费用记账、请求/响应脱敏留存、trace 串联、内容安全前置过滤。

### 3.2 分层路由表（"贵的做创意与评审，便宜的做批量"）

| 阶段 | 能力 | 档位 | 说明 |
|---|---|---|---|
| L1 发散 | chat | 中档 + 高 temperature（0.9–1.1），**每个组合独立调用** | 便宜模型也能发散，多样性来自采样策略 |
| L1 评分/去重 | chat + embed | 中/低 | 评分可用小模型；去重必须 embedding |
| L2 检索计划 | chat | 中 | 结构化输出查询列表 |
| L2 抽取/校验 | chat | 中 + 规则 | 抽取用强模型，交叉校验用规则 + 弱模型 |
| L3 大纲 | chat | **强模型**（低 temp 0.3） | 结构决定成败 |
| L3 逐节扩写 | chat | 强模型（0.7） | 并发、可单节重写 |
| L3 critic | chat | **强模型，且与写作不同供应商**（避免同源盲区） | 关键质量杠杆 |
| L4 分镜 | chat | 强模型（结构化输出） | 输出必须严格 JSON |
| L4 图像 | image | 中档 + 固定 seed + style token | 一致性优先于画质 |
| L4 视频片段 | video | 少量、限额 | 成本最高，占比 ≤20% |
| L4 TTS | tts | 中档，必须返回词级时间戳 | 时间戳质量决定对齐 |
| L6 事实核对 | chat + 规则 | 强模型 + 确定性校验 | 数字比对必须用规则，不用模型 |
| L6 视觉检查 | 视觉模型 + CV | 中档 + 传统算法 | 黑帧/静音用算法，构图用视觉模型 |
| L7 标题/封面 A/B | chat | 中 | 批量生成候选 |

**模型抽象要求**：业务代码只认 `capability + tier`，不认厂商名；换模型只改路由表。
**双供应商**：每个 tier 至少 1 主 1 备；主备在评测集上差距 ≤ 5% 才允许互为备份。

### 3.3 提示词规范（Prompt Engineering Spec）

1. **一阶段一提示词，禁止"万能 prompt"**；每个 prompt 有 `prompt_id@version`，纳入版本管理与评测。
2. **结构固定四段**：`角色与目标` / `输入数据（结构化）` / `硬约束（可校验的清单）` / `输出 JSON Schema + 示例`。
3. **强制 JSON**：输出必须符合给定 schema；附 1 个正例 + 1 个反例（反例展示常见错误）。
4. **约束前置、理由后置**：把可校验的硬约束放在最前，模型更容易遵守。
5. **温度按阶段设定**：发散 0.9–1.1；结构/分镜 0.2–0.4；扩写 0.6–0.8；评审 0.2。
6. **禁止在 prompt 里塞全量素材**：只给摘要卡（`research_brief`）+ 本节相关 facts，控制上下文 6–8k token。
7. **失败反馈闭环**：校验失败时把"哪里错了 + 期望是什么"回灌，而不是重跑同一个 prompt。
8. **prompt 变更必须过评测集**，并在 `run_manifest.versions.prompts` 里记录，保证产物可复现。

## 4. 成本模型（估算基线，需按实际询价校准）

### 4.1 单价假设（示意，用于容量规划，不含税）

| 项 | 单价假设 | 备注 |
|---|---|---|
| 强模型 chat | $2.5 / 1M 输入 tokens，$10 / 1M 输出 | 按主流中高端档位估 |
| 中档 chat | $0.4 / 1M，$1.6 / 1M | 发散、打标 |
| 图像生成 | $0.02–0.05 / 张 | 视分辨率 |
| 视频生成 | $0.10–0.40 / 秒 | 最大成本项，必须限额 |
| TTS | $0.05 / 千字 | 含时间戳 |
| 渲染（CPU） | $0.03 / 分钟 | 自建机器摊销后 |
| 存储/带宽 | 忽略（< 5%） | |

### 4.2 单条作品成本拆解（估算）

| 形态 | 主要成本 | 估算 |
|---|---|---|
| 图文长文 | L1 发散 40 次调用 + 研究 10 次抓取 + 写作/评审 + 6 图 | **$0.25–0.6（¥2–4）** |
| 卡片组 | 同上 + 8 张卡渲染 | **$0.15–0.4（¥1–3）** |
| 短视频 60–90s | 上述 + 40–60 镜头渲染 + 2–4 个生成片段 + TTS | **$1.2–2.2（¥9–16）** |
| 长视频 5–12min | 上述 ×3–4 + 更多生成片段 | **$4–8（¥29–58）** |

**降本杠杆（按效果排序）**
1. 镜头级缓存（改稿重出片成本降到 20–30%）；
2. 生成片段限额 + 优先图形组件；
3. 发散期用中档模型（数量多但单次便宜）；
4. 阶段级缓存（同一选题跨形态复用 L2/L3）；
5. 批量渲染（夜间错峰、GPU 分时）。

### 4.3 预算护栏
- 每 `run` 有 `cap_usd`（形态默认值可覆盖）；80% 预警降级，100% 终止。
- 每日总预算 + 每模型日配额；超限排队而不是失败。
- 成本按 `run/stage/day/platform` 四维记账，可回答"钱花在哪一层、哪一类内容 ROI 最高"。

## 5. 可观测性

| 维度 | 内容 |
|---|---|
| Trace | 一次 run 的全链路 span：stage → model call → tool call → render job，含耗时/成本/token |
| 指标 | FPR、弃稿率、各阶段耗时 P50/P95、单条成本、缓存命中率、队列深度、闸门等待时长 |
| 日志 | 结构化；提示词与响应需脱敏留存（含 prompt 版本），用于复盘与评测集扩充 |
| 告警 | 阶段失败率突增、成本超阈、闸门积压 > SLA、合规 critical 命中、发布失败、回采失败 |
| 看板 | ①今日产能与成本 ②质量分布（QA 分数直方图）③闸门待办 ④平台表现 Top/Bottom |

**SLO 建议**：单条短视频端到端 P95 ≤ 25 分钟（含人工等待另计）；发布准点率 ≥ 98%；QA 漏检（发布后被动下架）≤ 1%/月。

## 6. 安全、合规与版权

| 项 | 设计 |
|---|---|
| AI 生成标识 | 元数据 + 画面角标/描述声明双写；符合国内生成式内容标识要求；发布包里 `ai_label=true` 强制 |
| 素材授权 | L0 素材库入库即带 license/territory/expiry；无授权不得入库；`asset_manifest` 缺字段 → QA critical |
| 肖像与商标 | 真实人物/品牌出镜需授权记录；默认策略：不生成可识别真人、不出现第三方 logo |
| 行业敏感 | 医疗/金融/法律/教育断言走白名单来源 + 免责声明；无资质则禁止给出建议性结论 |
| 数据与隐私 | 用户提供素材单独存储、可删除；提示词与产物留存策略与删除机制明确 |
| 账号安全 | 发布账号凭证集中托管、最小权限、操作审计；全自动发布保留一键熔断开关 |
| 审计 | 每条作品可回答：谁批准、用了什么模型与版本、素材从哪来、改了几次、为什么改 |

## 7. 部署形态

```
┌───────────── API / 调度入口（HTTP + 定时 + IM 指令） ─────────────┐
│  Orchestrator(Temporal) │ Gate Service │ Scheduler │ Cost Guard   │
└───────────┬───────────────────┬──────────────────┬────────────────┘
            │                   │                  │
     ┌──────▼──────┐    ┌───────▼───────┐   ┌──────▼──────┐
     │ Worker: LLM │    │ Worker: Render│   │ Worker: GPU │
     │ (无状态/弹性)│    │ (CPU, Remotion│   │ 图像/视频/TTS│
     └──────┬──────┘    └───────┬───────┘   └──────┬──────┘
            └───────────┬───────┴──────────────────┘
                   ┌────▼─────┐   ┌──────────────┐
                   │ Postgres │   │ 对象存储 S3  │
                   └──────────┘   └──────────────┘
```

- 早期可单机 docker-compose（降运维成本），但**存储与队列语义必须是分布式的**，避免二次迁移。
- 渲染容器内固定字体、Chrome/Node 版本、LUT 与组件版本（渲染一致性）。
- GPU 池按需伸缩；夜间批量渲染省钱。

## 8. 配置项清单（必须外置，不写死在代码里）

| 配置 | 内容 |
|---|---|
| `platform_specs` | 各平台尺寸/时长/码率/标题字数/标签数/发布时段 |
| `thresholds` | 03 的全部阈值，带版本 |
| `model_routing` | 阶段 → tier → 供应商与参数 |
| `budgets` | 形态默认预算、每日总预算、模型配额 |
| `style_tokens` | 品牌视觉参数（多套，按账号/栏目） |

| `banned_phrases` / `sensitive_terms` | 词表，可热更新 |
| `content_matrix` | L1 选题矩阵枚举与权重（bandit 可写） |

## 9. 设计层面的"不要做"清单

1. 不要用单一超长 prompt 串全流程；
2. 不要在没有自动 QA 的情况下开自动发布；
3. 不要用"逐帧拼图"思路做视频（timeline + 图层 + 组件，没有例外）；
4. 不要引入无版权元数据的素材；
5. 不要为了省事把闸门做成"必须人工逐条看"；
6. 不要让业务代码直连模型厂商（一定要过网关）；
7. 不要在 P1 之前投入渲染工程（先用图文验证内容质量假设）。
