## ① 机制层提炼（不是复述，是拆出可迁移的机制）

文章的总命题：**人的注意力是系统里最稀缺、也最先被打爆的资源**（引 DeepSeek《Super-agent 设计探索》："一个人通常只能同时跟进 3–5 个活跃会话；单任务上限取决于模型能力，多任务上限取决于人的注意力"）。它给出的解法不是"更强的 Agent"，而是**把任务的起点从人身上搬走**。落到 6 个机制：

### M1 事件层：任务起点从"人下命令"改成"信号到达"
- 一切触发都归约为*事件*：定时轮询、Webhook、消息、邮件、告警。
- 所有事件先汇进一个**很小的独立服务（自动化中台）**，由它统一决定"交给谁、什么时候叫醒、结果怎么收回"，只有需要人决策时才弹飞书卡片。
- 反面判据（文章原话的意思）："所有事情的起点都是你，你只要不打开那个窗口，什么都不会发生"——这就是没有事件层的症状。
- 定时轮询解决不了及时性（同事提意见、线上报错），必须 Webhook；两者最终被并进同一套。

### M2 事件信封 + 规则表：把"接一种新事件"的成本压到改一行配置
- 事件统一格式：`来源 / 类型 / 对象 / 一句话摘要 / 回原处的链接`（例：`feedback.new #12`）。
- 路由写在 `rules.json` 一条条规则里，字段实测为：`name / when{source,types[]} / to(哪个 Agent) / cwd / skill / ask(一句话指令) / group(互斥组) / parallel(并发上限) / tell("needed" 才叫人)`。
- 收益：接新事件=加一条规则（几分钟生效，不用写脚本）；换模型/换 Agent=改一行字；**解耦点在于"规则"与"执行"分离**。

### M3 拉取式派活（反向连接）：执行体在内网，中台在外网
- Webhook 推不到家里/办公室内网的 Mac，于是反过来：每台 Mac 上跑一个**常驻接单程序**挂在中台上长轮询（一次最长 50 秒），有活立刻接走。速度接近实时推送，且**不用把执行机暴露到公网**。
- 为什么坚持本地执行：代码仓库、发布权限、飞书身份、已登录各账号的 Chrome 全在本机；上云要处处复制凭证（既麻烦又不安全），且国内站点/微信类浏览器任务在海外云上直接不可用。

### M4 统一去重 + 单一出口 + 数据沉淀（中台的三个"副产品"其实才是主价值）
- **去重**：自动化跑起来后"同一件事被发好几遍是常态"（网络抖动重发、同事补一句话、补一张图）。每条都唤醒 Agent = 同一件事多个 Agent 并行乱改。去重放在中台做，不放各流水线做。
- **单一出口**：所有 Agent/任务找人只走一条路（飞书 AI 助理卡片），且每条规则显式声明 `tell: needed`——"只在必须我判断决策时才说"，避免这个脚本发一条那个机器人发一条把飞书刷屏。
- **数据沉淀**：所有事件过中台 → 每条都有底（何时来、从哪来、交给谁、结论、是否需留意、后来怎么解决），**点开任务能直接跳回当时 Agent 干活的那个会话**。攒久了就是"哪条流水线最忙、哪个 Agent 干得最多、哪类事老出问题"的数据依据。

### M5 人的接口 = 票拟批红：卡片不是通知，是"已经替你做好了，请盖章"
- 借明代票拟/批红：Agent 先把处理意见写好贴上来（票拟），人只看一眼红笔批（批红），点完 Agent 接着往下干、卡片自己改成结论。
- **关键不是卡片交互，而是"什么该推给人"的白名单**：删数据、停服、花钱、对外发消息、改产品方向、新建/轮换密钥、修改权限——其余全自动做完上线。文章自陈踩过"一天推几十条，严重占用注意力"的坑。
- **决策台账**：仓库里两份文件——「定的事」（只记亲口决定，带原话+日期）、「定了不做的事」（拒绝过的，Agent 照答、不再来问）。规则：**定过的事不问第二遍**。
- 唯一不交给 Agent 的：用户反馈，人必亲自看、亲自挑，再交给 Agent 执行。

### M6 质量闭环靠"审查者硬约束"，不靠"更聪明的审查者"
- 五步自动化交付：审查 → 检查 → 合并 → 发布 → 核实（中位 2–3 分钟），**写作者与审查者必须是不同模型**（Claude 写、GPT 审）。
- 审查者的四条硬约束才是关键：**只读（不能改）、不联网、拿不到密钥、只报真会出错的问题不报风格**；并且**最多审 3 轮**（学 Anthropic Claude Code 团队做法），否则会出现"无限挑错磨磨唧唧"。
- 实测：4 个项目 298 个 PR、报 333 条问题、合并前修掉 306 条、最严重档 51 条；单次审查中位 2 分多钟，占该任务 token 的 5–15%。
- 组合原则：**决策/管理用最强模型**（"不能用笨逼指挥聪明的"），执行按性价比分派（开发=Opus、运维=Sol、浏览器操控=Terra）。
- 每个自动化任务配一个专属 **Skill**（=沉淀给 Agent 的 SOP：规则+参考+脚本），改任务只改 Skill、不改执行逻辑——解耦。

## ② 逐项对照表

评级：✅一致（我们已有且同向）｜⚠️差异（我们有形但机制不同/更弱）｜❌缺（没有该机制）｜💡借鉴（可低成本吸收）

| # | 文章机制 | 我们 v0.3/v0.4 的现状 | 评级 | 说明 |
|---|---|---|---|---|
| 1 | 事件层：信号触发，不由人下命令 | `orch.run.create` 是唯一入口，**由人发起**；无事件源、无触发器、无轮询/Webhook | ❌ | 这正是文章点名的"起点在你身上"症状。我们的闭环只有"发布→回采→L1 权重回灌"，**回采只改权重、不触发新一轮**，跑起来仍需人点下一次 |
| 2 | 事件统一信封（来源/类型/对象/摘要/回链） | 有 `StageResult` 信封（run_id/stage/inputs_hash/producer/cost），是**产物**信封不是**事件**信封 | ⚠️ | 两者不冲突，可并存：事件信封管"进来的活"，StageResult 管"出去的产物" |
| 3 | 规则表路由（who/model/depth/并发/是否叫人） | `model_policy` 只有 `cheap/standard/premium` 三档 + `domain_pack` 配置包 | ⚠️ | 我们缺"事件类型 → Agent+模型+推理深度+并发+是否叫人"这张**路由表**；`domain_pack` 管内容先验，不是调度 |
| 4 | 去重（同源重发/追加合并） | 有 `idempotency_key`（同一次写操作幂等）、`dup_cluster_id`（选题语义去重）、`inputs_hash` 缓存 | ⚠️ | 幂等 ≠ 事件去重：`feedback.new` 与 `feedback.followup` 在文章里是同一件事的两个事件、要并成一组；我们只在 L1 内部做了去重 |
| 5 | 单一出口 + `tell:needed` 推送纪律 | 三闸门各推卡；有 SLA/超时策略，但**没有"该不该叫人"的判定规则，也没有每日卡片上限** | ⚠️ | 按默认 3 条/日 × 3 闸门 ≈ 9 张卡/天，正好踩在文章踩过的坑边上；M2/M0 挡位能缓解，但缺硬上限 |
| 6 | 决策白名单（删数据/停服/花钱/对外发/改方向/密钥/权限） | `R2/R3` 风险分级 + `gate.escalate`；G3 卡住"对外发" | ⚠️ | 我们有"内容风险"分级，缺"**动作后果**"分级（花钱、改配置、动账号、改方向）——两者正交，都要 |
| 7 | 决策台账（定的事/定了不做的事，带原话+日期） | `domain_pack.forbidden_clichés` + P1 §0.1 决策记录表（人写的文档） | ⚠️ | 我们是**文档里的表**，机器不读；要用起来必须是**结构化 ledger**，否则同一件事还会被问第二遍（本项目 2 天内已经问过一轮 10 题） |
| 8 | 票拟批红：卡片=建议+一键批 | 现在是 G1"从 3–8 挑"、G2"看 thesis+前 3 段"、G3"看封面+首屏"；v0.4 已提"默认通过、只否决" | ⚠️→✅ | 方向一致，v0.4 只差把卡片从"选择题"改成"**建议+理由+一键批红**" |
| 9 | 人参与度分级 M0–M3 | 已有 M0–M3 + 自动降级规则（连续 10 条 FPR≥70% 转自动放行） | ✅ | **比文章更细**：文章只有"白名单+不问第二遍"，我们有挡位与降级阈值。反过来，我们的降级**缺一个前置条件**——必须先有"事件层+去重+单一出口"，否则 M0 等于无人看守的定时炸弹 |
| 10 | 执行体本地常驻 + 内网回连（长轮询） | 控制面/数据面全在"服务"里（编排器、模型网关、渲染队列），假定云端 | ⚠️ | 我们的发布面恰恰最需要本地：公众号/小红书后台登录态、`manual_fallback` 的一键发包、本地素材库。`pub.capabilities` 只做了能力探测，没解决"登录态住哪儿" |
| 11 | 写作/审查分离 + 审查者硬约束（只读/不联网/无密钥/只报真错/最多 3 轮） | L6 有四类检查（事实/合规/去陈词/平台）+ `qa_report.attempt≥3 → discard`；`verify` 已分"只降不消" | ⚠️ | 我们**没有写"审查者角色权限"**（只读、不给密钥、不联网）；"最多 3 轮"我们有等价物；但"**不报风格**"与我们的"去陈词/AI 味"检查直接冲突（见拍板点 5） |
| 12 | 每任务一个 Skill（SOP 解耦） | `prompt_id@ver` + `domain_pack` + 模板版本落库 | ✅ | 思路一致；可以更彻底：把"一个任务的 SOP（规则+参考+脚本）"打成可独立改的包，与流水线代码解耦 |
| 13 | 决策/管理用最强模型，执行按性价比分派 | `gw.complete` 的 tier 三档 + `model_policy_ceiling` + 预算闸门 | ✅ | 一致；可补一句硬规则："**质量判定与闸门建议必须用 ≥standard 档，不得用 cheap**" |
| 14 | 数据沉淀 + 任务→会话可跳回 | Postgres/对象存储存 run/stage/artifact、`audit.trace` 全链路、`feed.join` 质量分对照 | ⚠️ | 我们留了"产物与成本"的底，缺"**决策与会话**"的底：文章那条"点开任务能跳回 Agent 当时的会话"是排查与复盘的性价比之王 |
| 15 | 流水线可视化（种田游戏爽感） | 无（只有 audit 与日报） | 💡 | 低成本、高士气，且顺手暴露"哪条线堵了"。P2 可做，别进 P1 关键路径 |
| 16 | 发布后核实（五步的第五步） | `pub.verify` → `live_check`（可访问/标识可见/图片完整） | ✅ | 我们有；文章的价值是把它做成**强制最后一步并写回上游**（结果回写、Agent 看得到终态），我们目前只是输出，没规定"必须回写并关闭 run" |
| 17 | 全自动到"上线"（Agent 交 PR 即止，CI 接管） | 我们全自动到 G3 为止，P1 明确"质量不能靠机器兜住" | ✅（有意差异） | 内容生产缺"编译/测试"这类客观判据，事实与合规不能靠 CI 兜住 → **我们的闸门不能像他一样退到 M0 那么快**，这是要保留的差异，不是要补的缺口 |

## ③ 需要拍板的取舍点（5 个，附我的建议）

1. **要不要在 P1 加"事件层"（L-1）？**
   最小版：3 个信号源（热点榜/下拉词变化、评论区新疑问、同类爆款更新）+ 一张 rules 表 + 每日一次"要不要开工"的自主判断 + 事件去重 + `tell:needed`。
   代价约 +3 天（P1 从 10 天到 13 天），收益是把"起点从人身上搬走"这条主命题真正落地。
   **建议：进 P1，但只做"自主立项"一段（选信号 → 生成 run 建议 → 卡片批红 → 自动开跑），不做全站事件中台。**

2. **闸门形态：改成"票拟式"吗？**
   即卡片预填"我建议这条这么做，理由 X，如不同意点否决"，替代现在"从 3–8 里挑"。
   **建议：改。G1 改"默认通过+只否决+事后抽检"（v0.4 已提），G2/G3 卡片头部加"建议+一句话理由"。**

3. **注意力预算要不要写成硬约束？**
   建议定：**主线 ≤6 张人工卡/天**，超限的排队或转抽检；"花钱/对外发/R2/改方向"四类不受上限约束（永远必推）。
   **建议：写进 `gate.request` 契约。**

4. **决策台账要不要落地成结构化文件？**
   （"定的事 / 定了不做的事"，带原话+日期，Agent 每次先查）
   **建议：落，`decisions_ledger@1`，P1 就把已有的 15 条决策灌进去。这是防止"同一件事问第二遍"的唯一解。**

5. **"不报风格"这条要不要照抄？**
   文章要求审查者只报"真会出错"，不报"可以写得更好"；而我们的 L6 有"去陈词/AI 味"检查——那本质是风格。照抄会丢掉我们的差异化（反 AI 味是我们的核心卖点之一）。
   **建议：分层——"事实/合规/平台规则"三类只报硬错（照抄他的纪律）；"去陈词/AI 味"单列为风格门，**不阻断发布、只进评分与反驳材料**。**

**附一条不占拍板位但值得知道的**：他坚持本地执行（登录态/密钥在 Mac 上）。我们的发布面同理，若 P1 要真跑公众号/小红书，登录态与一键发包放本地还是云端，会在 D8–D9 变成硬问题，早定比晚定省事。
