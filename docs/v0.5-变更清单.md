## 变更 0：素材与参考的来源改为 Obsidian 仓库（影响最大的那条）

**你的原话**：「第一点的事件，如果是搜索网络信息这部分，我打算交给另一套系统去做，当前工作流的素材和参考视频等等全部都从 obsidian 仓库里面获取即可。」

### 0.1 我的理解（请确认，见 §4 问题 a/b/c）
- **不做外部信号监听**：热点榜轮询、搜索下拉词、竞品更新、评论区挖需求——这一层整体不做，**由另一套系统负责**，本工作台不重复建设。
- **工作台的输入边界 = Obsidian 仓库**：素材（图/视频/文档）、参考视频、灵感笔记、已核实的事实与出处，全部从仓库读。
- 因此"事件"缩小成两种，**不引入 webhook 中台**：
  1. `vault.new`：你往仓库里放进新素材/新灵感 → 工作台感知到新条目即立项；
  2. `cron.daily`：每日固定时间扫一次仓库，判断"材料够不够开工"（够就出选题请示卡，不够就只发一条"今天材料不足，缺 X"）。

### 0.2 对分层的具体改动
| 层 | v0.3 | v0.5 |
|---|---|---|
| L1 选题 | 检索驱动（热点/下拉词/评论）+ 矩阵抽样 + 红队反陈词 | **矩阵抽样 + 红队反陈词保留**；"检索驱动"改为**仓库驱动**：从 `vault` 的笔记/素材/标签里抽 `demand_seeds`；40 选 3–8 不变 |
| L2 取证 | `research.search/fetch/trends` 打网络，source_tier S1–S4 | 改为 `vault.search / vault.fetch / vault.assets`，**本地优先、缺口上报**；网络检索接口保留但默认关闭（留给另一套系统回灌） |
| L0 资产 | 事实源白名单 | 增加"仓库契约"：笔记 frontmatter 规范（见 0.3）；白名单改为"`origin` 域名白名单" |
| I9 回采 | 平台数据回采 | 增加**回灌仓库**：发布后数据 + 复盘结论写回 Obsidian（形成你自己的知识资产，而非只留在系统里） |

### 0.3 必须新增的一条硬规矩：**本地库 ≠ 可信来源**
把取证从线上搬到自己仓库，最大的风险不是"内容不够"，而是**自我循环论证**——素材是自己收集的、出处也是自己记的，`fact_sheet` 会变成"自证"。

所以 `fact_sheet@1` 的 `source_tier` 判定对象改为笔记里的 **`origin` 字段（原始出处 URL/文献/实验记录），不是笔记本身**：
- 笔记带 `origin` 且 origin 属 S1–S3 → 该断言可用；
- 笔记**没写 origin** → 断言一律降为 `S4/unsourced`，只能作观点、不得进正文断言（`verify` 直接判 `unsupported`）；
- 笔记 origin 之间互相矛盾 → 进 `red_flags`，触发异常请示卡。

配套：笔记 frontmatter 最小字段集（缺字段的笔记进 `vault.reject` 清单，不静默使用）
```yaml
title: str
kind: note | image | video | doc | data
origin: url | 文献标识 | experiment_id   # 空 = 不可进正文断言
fetched_at: date
license: own | licensed | generated | reference_only   # 图片/视频必填
tags: [主题, 角度]
```
> `reference_only` 的素材（含参考视频）沿用 D12：只作启发，**不进成稿像素**。

### 0.4 需要你确认的三件事（阻塞 D3 的 L1/L2 试跑）
- **a. 仓库怎么接**：工作台与仓库在同一台机器（本地目录只读挂载）／git 同步／还是只读 API？决定我用哪套接口实现。
- **b. 现有笔记有没有 frontmatter**：如果没有，我可以出一个"补元数据"的批处理（只补不改内容），或者退一步——**入库时由你填三格**（origin / license / tags），我做成一个 10 秒能填完的小卡。
- **c. 参考视频的用法**：确认只作 `reference_only`（看结构、看节奏、看钩子），不做二次剪辑、不进成片；若要"逐字引用或截取画面"，会触发强制标注（§5.1 已定）。

# 附录 A：15:03 追加答复后的收敛（仓库接入 / 元数据 / 参考视频 / 术语）

## A1 仓库接入：做成适配层，不锁死协议

你的答复：「仓库不一定会存在本机，但肯定放在虚拟局域网内的一台设备上，放开端口访问即可」。

所以不按"某个协议"设计，按**一个只读适配接口 + 可换驱动**设计：

```
vault.index(since)            -> entry[]  {path, mtime, sha256, frontmatter}
vault.search(query, tags, kind) -> hit[]
vault.read(path)              -> {body_md, frontmatter, attachments[]}
vault.asset(path)             -> bytes + license
vault.changed(since)          -> 变更流（轮询 mtime / SSE）
```

驱动按你的实际环境择一，代码上层不变：

| 驱动 | 前提 | 优点 | 代价 |
|---|---|---|---|
| `http_rest`（建议） | 仓库那台装 Obsidian **Local REST API** 插件，开端口 | 直接拿 frontmatter/搜索结果，不用挂载 | 需要装一个插件 |
| `webdav` | 端口后面挂静态目录（WebDAV） | 不依赖 Obsidian | 只能读文件，frontmatter 自己解析 |
| `smb/nfs mount` | 虚拟局域网内挂成本地目录 | 最省事，当本地目录读 | 依赖挂载稳定性 |
| `git` | 仓库走 git，工作台定时 pull | 有版本历史，天然增量 | 有推送延迟 |

三条硬约束：
1. **只读凭据**，工作台不回写你的库；唯一例外是我另开一个 `inbox/系统复盘/` 只写目录，供"发布数据 + 复盘结论回灌"（见变更 0.2 I9），你不想开就不开。
2. **不暴露公网**，只在内网/虚拟局域网；token 走 header。
3. **建本地索引**（sqlite + 文件哈希），不每次全库扫描；变更检测靠 `mtime+sha256`，不是靠"每分钟重扫"。

## A2 元数据：存量与新增两轨，且两类字段不许机器补

你的答复：「目前没有（frontmatter）」。

两条铁律先说：
- **可以机器补**：`title`、`kind`、`tags`（错了能改、代价低）。
- **不许机器补**：`origin`（原始出处）、`license`（授权）。理由：让模型读正文"推断"来源，它会**编一个看起来很像的 URL**——这比没来源更坏，等于给自证盖了个假章。这两项只能：你确认，或标 `unsourced`。

于是分两轨：
- **存量（一次性）**：Agent 逐篇读正文，产出 `title/kind/tags` 候选 + 一个 frontmatter 补丁 diff（**只加字段、不改正文一字**）→ 你只审 `origin` 与 `license` 两列 → 你点同意才写。按你库的规模，这一步可以按主题分批做。
- **新增（长期）**：入库小卡，三格 10 秒填完：`origin`（粘贴链接或标"无出处"）、`license`（own/licensed/generated/reference_only）、`tags`（可点选）。填完即入库，不填则素材进 `pending` 清单，**不进入任何正文断言**，但可以当观点or灵感用。

## A3 参考视频：不做素材，做"风格样板"（升级用法）

你的答复：「主要做参考，用来学习风格、动效等等，不是一定要用进成片内」。

那它不该留在 `reference_only 素材` 这一类里（那只是"不用"，浪费了），应该升格成一类资产：`style_sample`，由它抽参数、落 `style_token@1`，供 L4 版式 / L5 渲染直接读：

| 抽什么 | 具体参数 | 用在哪 |
|---|---|---|
| 钩子 | 前 3 秒做法、首句句式、开场镜头类型 | L3 开头写法 / L4 首屏 |
| 节奏 | 镜头时长分布、字卡停留时长、信息密度曲线 | L4 时间线 / L6 风格层检查基准 |
| 结构 | 段落切点、转场位置、章节卡位置 | L3 大纲 / L4 |
| 动效 | 转场类型、运动曲线、字效、图表入场方式 | L5 渲染 |

边界（延续 D12，不放松）：**只抽参数，不截取画面、不二次分发、不进成片像素**；抽取产物是"数值与描述"，不是"画面"。副产品：它同时成为"去 AI 味"的客观基准——风格层检查拿 `style_token` 当参照物，而不是靠模型"感觉像不像人写的"。

## B2 那"事件层"还剩什么？只剩两种，且都不产生动作

| 信号 | 用途 | 明确不做 |
|---|---|---|
| `vault.new` 新素材入库 | 建索引、可被检索（供入口③推荐时用） | **不触发立项**、不弹卡片 |
| `vault.changed` 笔记更新 | 索引增量刷新 | 不触发重跑 |

也就是说：**没有事件驱动的开工**。事件层退化为"索引层"。这也顺带确认——文章那套自动化中台，对我们**只有"素材入库即索引"的价值，没有"事件即立项"的价值**。（这条差异要写进正式方案，避免以后有人照着文章又搭一遍中台。）

## B3 推荐引擎规格（入口③专用，唯一需要"主动"的地方，由你叫醒）

### 三源交叉：候选必须同时站得住三只脚
1. **已发内容台账**：近 90 天发过什么（去重、找续集、找反差角度）。重复角度直接丢弃。
2. **数据表现**：哪类角度真有效（完读/收藏/涨粉），按 `feed.join` 的对照表加权；数据不足时 **明确降权并标注"数据不足"**，不假装有依据。
3. **仓库素材可用性**（这条最硬）：每条候选必须能点名"用仓库里哪几条素材/笔记支撑"。**点不出料的候选不许出**——宁可只给 3 条，也不给 8 条空想。

### 候选卡（仍是票拟，不是清单）
每条候选给：一句话题眼 + 凭什么（三源各一行）+ 手上有多少料（素材条数/原始出处数）+ 预估成本 + 风险（是否触 R2）。整卡**预勾选我推荐的 1–3 条**，按钮仍是同意/拒绝/自定义回复。

### 推荐质量的自检（防止"推荐=模型瞎想"）
- 每条候选的"料"必须可枚举到具体文件路径，不可枚举即视为无料；
- 候选里至少 1 条要是"从数据反推"的（哪类角度有效→再做一期），不能全是"仓库里有啥就推啥"；
- 若仓库中能支撑的素材总量不足 N 条，直接回你"现在库里能撑起的只有 X 个方向，建议先补料"，**不硬凑候选**。

| 层 | 内容 | 变更性 | 空值允许 |
|---|---|---|---|
| `topic_preference` **软先验** | 大类=AI（宽口径：工具、使用体验、如何做出作品、方法、案例……都是合法子域）；只是给候选打分的加权项 | 随时改，改它不影响流水线 | **允许为空**（空=完全按数据与素材走） |
| `quality_pack` **硬配置** | 风格 token、禁用陈词、合规档位、平台限额、风险规则、出处策略 | 相对稳定，改动要走评审 | 不允许为空 |

关键：`topic_preference` **只能加权，不能拦截**。它是"我猜你更想看这个"的排序依据，不是"这个话题不许做"的门。出现"因为不在赛道里所以不做"= 实现错了。

## B5 一个风险，先说在前面

仓库现在没有 frontmatter（D22：存量暂不动）。这意味着**素材可用性索引一开始会很弱**——没有标签，我只能靠目录名和全文检索判断"这条素材能撑什么话题"，推荐准确率会打折。

缓解（不额外增加你负担）：
1. 新素材入库三格小卡里的 `tags` 就是为这个用的，从现在开始积累；
2. 我出推荐时**把"依据哪几条素材"逐条列在卡上**，列不准你一眼能看出来并否掉；
3. 攒够一个月，我出一份"仓库素材 × 已发内容"的覆盖图给你看，那时候再决定要不要清理存量。
