# 多平台扇出规格 v1（一个话题 → N 条平台流水线）

> 触发：2026-11-02 15:23「如果打算一个话题发布好几个平台，每个平台都需要一个流水线……发布一个话题后，接受中控台主动唤醒三条流水线并发制作」。
> 结论先给：**方向对，但不能是"三条完整流水线从选题开始并发"**——那样成本 ×3、证据会互相打架、一天六张卡。正确形状是**一个话题一次研究，在"成稿"处扇出，在"版式/质检/发布"处彻底分叉**。

---

## 1. 先纠一个形状：扇出点不在起点，在中段

### 1.1 为什么不建议"三条流水线从头并发"
| 问题 | 后果 |
|---|---|
| 选题各跑一遍 | 3 份候选互不相同 → 你批完还是三个不同话题，不叫"一个话题发三处" |
| 取证各跑一遍 | 三套事实、三套数字、三套出处 → 公众号说 A、抖音说 B，读者一对比就露馅；成本 ×3 |
| 三道闸门 × 3 平台 | 一天 6–9 张卡，正好回到你之前说的"别刷屏"的反面 |
| 一个平台失败 | 若串在同一 run 里，另外两个被拖住 |

### 1.2 正确的形状：共享上游，分叉下游

```
你给题
  │
[L1 选题]  ── 一次
  │
 ✋ G1 选题卡（一次，问"这题发哪几个平台、以哪个形态为主"）
  │
[L2 取证]  ── 一次，产出唯一一份 fact_sheet（版本锁定）
  │
  ├──────────── 扇出点（fanout）────────────┐
  │                 │                        │
[公众号 长文]   [小红书 卡片组]         [抖音 竖屏视频]
  │                 │                        │
  ├─ 各自 G2（文稿/文案/分镜）  ← 每平台一张独立卡
  │                 │                        │
[排版]           [卡片版式]              [分镜+渲染]
  │                 │                        │
  ├─ 各自质检（平台规则不同）+ 家族 G3 发布卡
  │                 │                        │
[发布]           [打包一键发]             [发布]
  │                 │                        │
  └──── 各自回读核实 + 各自回采数据 ────┘
```

**一句话**：真正需要按平台独立的只有四件事——**文体、版式/渲染、平台规则质检、发布适配**。选题与取证必须共享。

## 2. 主形态（master form）：扇出前必须先定一个"母版"

三平台同时开做，最大的隐坑不是成本，是**三套叙事各讲各的**。所以要显式选一个母版，其余从母版派生：

| 母版 | 适合 | 派生方向 |
|---|---|---|
| **视频优先**（口播/分镜先行） | 这题的杀伤力在演示、对比、过程感 | 分镜 → 抽关键帧/要点 → 公众号长文 → 卡片组 |
| **图文优先**（长文先行） | 这题的杀伤力在论据、数据、可查证 | 长文 → 抽要点 → 卡片组 → 口播稿/分镜 |

规则：
- `fanout_policy.master_form` 必须在 G1 卡上让你看见并可选（默认我建议，你可以改）；
- 派生不是"重写"，是**同一 narrative 的重新组织**：母版定义"讲什么、什么顺序、什么结论"，子形态只改"怎么呈现"；
- 母版先落地（一次），派生产物引用母版的 `narrative_id`——**任何子形态擅自引入母版没有的新论点，质检直接拦**。

## 3. 一致性硬规则（这条是整套扇出的地基）

1. **一份事实**：同一 topic 的所有平台产物，引用**同一个 `fact_sheet_id@version`**。要改事实 → 改事实源、升版本、自动触发其他平台"漂移复核"（只查"新增/修改的断言是否与我已经发的那句冲突"，很轻）。
2. **一个论点集**：母版的 `thesis` + `claims[]` 是唯一论述口径，子形态只能删减、不能新增。
3. **口径校验在 G3**：发布卡上直接显示"三平台关键数字一致性：✅ 一致 / ⚠️ 公众号¥9.9 vs 抖音¥10"。
4. **数字优先取整源**：涉及价格的，三平台用同一取整规则（如统一"约 10 元"），避免"¥9.9 / ¥10 / 十块"三种说法。

## 4. 闸门卡片：不合并，每平台各自一张（15:29 你的决定）

你的决定：**暂时不合并卡片**。那么扇出后的卡片数 = 平台数 × 2（每平台一张文稿卡 + 一张发布卡）。

| 阶段 | 每话题卡片数 | 说明 |
|---|---|---|
| 先做图文（公众号 + 小红书） | 4 张 | 一天一题 4 张，两题 8 张 |
| 再加视频（+抖音） | 6 张 | 到时候若觉得吵，随时改 |

我不再提"合并卡片"。但减噪还有三个**不违反你这个决定**的手段，只做这三个：
1. **卡片变短**：每张卡只讲自己平台的三件事（论点是否与母版一致、开头三句、缺口与风险），不复述全文——短卡比合并卡更容易看；
2. **到达时间错开**：同一话题的多张卡按上游完成顺序推，不一次性齐发，不打断你正在看的那张；
3. **可选的临时授权**：你在第一张卡上勾一句"其余平台按同一母版放行"，等于你**临时授权**我往下走，不是我偷偷合并——这个勾你随时可以不用。

一条不动的规则：**视频那张卡永远单独批、且最先批**，因为它花钱最多。

## 5. 成本与预算：扇出前先算账，难度分层

| 平台/形态 | 相对成本 | 处理 |
|---|---|---|
| 公众号长文 | 低（1×） | 独立卡，正常批 |
| 小红书卡片组 | 低（约 1.2×，多一次渲染） | 独立卡，正常批 |
| 抖音竖屏视频 | **高（约 8–20×：分镜+渲染+TTS+对齐）** | **单独批**，且 G1 卡上就给出预估，不许"批了才知道贵" |

预算规则：`topic_run` 有总预算（例：单话题 ≤¥25），各分支有子预算；子预算超支只停该分支、不拖累其他分支。**一次扇出的总预估必须在 G1 卡上出现**——这是"花钱必问"的落点。

## 6. 失败隔离：一个平台挂了，不许连坐

- 每条平台分支 = 独立状态机、独立重试、独立产物仓库路径；
- 父状态取聚合：`全部完成 / 部分完成（抖音渲染失败，已转手动）`，**不许整体标失败**；
- 重跑粒度：`orch.run.replay` 支持到"只重跑抖音分镜"这一级；重跑不重跑取证（引用同一 fact_sheet 版本）；
- 已发布的分支不许被父级重跑影响（发布是单向动作，重跑只产生新产物、不撤旧文）。

## 8. 范围边界（必须说清，别让你等一个做不到的东西）

你举的三条里，**抖音视频属于"再加视频"那一步**（此前已定：先做图文，视频层只留接口占位）。所以：

| 阶段 | 扇出实际能力 |
|---|---|
| **第一步（图文阶段）** | 一个话题 → **公众号长文 + 小红书卡片组 两路并发**（共用一次取证、一份事实、一个母版），每平台独立卡 + 双平台发布 + 各自回采 |
| **第二步（加视频阶段）** | 加第三条（抖音竖屏视频），扇出架构**不改**，只加一个分支实现 |

关键承诺：**架构现在就按 N 路扇出做**（父/子任务、每平台独立卡、一致性校验、失败隔离全部在第一步就位），第二步加分支只是"多接一个平台"，不是重构。这样你不会遇到"做了视频发现前面全要重写"。

## 10. 术语（以后不再出现 P1）

"P1/P2/P3"是我从设计文档里带出来的**批次编号**，对沟通没有帮助。以后只说人话：

### 11.2 我建议加的一道"风险闸"：先出 60 秒样片，再铺全流程
理由：视频这条线一旦方向错，返工的是渲染管线而不是文案。所以在 D7 前后先交一支 **60 秒样片**（真分镜、真配音、真动效、真字卡），你只看三件事：
1. 还是不是"图片切换"（你最初的三大不满之一）；
2. 节奏能不能撑住 3 秒留存；
3. 成本与时长是否落在我给的区间内。
样片不过关就停在渲染层调，不往下铺三路并发。**这一步大约多花 2 天，但能省掉后面十几天的盲跑。**

### 11.4 必须早核的一件事：抖音的发布通道
抖音大概率**不对个人号开放内容发布 API**（企业资质/权限申请另说）。若如此，抖音走**打包 + 一键发清单**，与小红书同路径——这不是缺陷，是现实边界，但要在 D2 就确认，否则工期承诺是空的。同理要核：视频的**平台 AI 生成标识**在抖音侧的声明方式（《标识办法》义务不因平台而变）。

## 12. 时间口径：为什么不该有"工作日"（15:33 你问）

你问得对，这个说法是我从人做项目的惯性里借来的，放在这套系统里是错的。

### 12.1 "工作日"错在哪
它默认了三件事，而这三件在这里都不成立：
1. 默认**干活需要连续的人力天数**——实际是 Agent 在跑，一轮可能是 20 分钟也可能是 2 小时，跟"天"没有换算关系；
2. 默认**工时是瓶颈**——实际瓶颈是**等你拍板的次数**和**外部客观等待**；
3. 默认**排期可预测**——实际只有"节点先后"是确定的，日历时间不确定。

### 12.2 真正决定时长的是三类东西
| 类别 | 内容 | 是否可压 |
|---|---|---|
| **你的介入** | 你的每张卡批一次、每次改方向、每次给料（仓库 token、平台资质信息） | 可以：改卡片质量、改问的频率（但你已定"不确定就问"，所以这类会偏多） |
| **外部客观等待** | 平台资质核验、内容审核、发布限流；回采数据要攒 7–14 天才形成"质量分 vs 数据"对照 | **不可压**，这是自然时间 |
| **我的执行轮次** | 每次"改完→跑一遍→验一遍"算一轮；渲染管线这类一次出片就要跑几分钟到十几分钟 | 半可压：并行、缓存 |

### 12.3 换成节点制（12 个节点，取代原来那张"按天"的表）
节点只保证**先后与验收标准**，不承诺日期。每个节点结束我给你一张"节点完成卡"（产物在哪、花了多少、下一步要你做什么）。

| 节点 | 交付 | 验收（可判定，不是"我觉得行"） | 卡在这一步的是谁 |
|---|---|---|---|
| N1 | 契约冻结 + 仓库接通 + 三平台发布通道核实 | Local REST API 能读能检索；三平台发布参数/资质查清并写明"能否 API 发" | **你**（给仓库地址与 token）＋ 平台 |
| N2 | 选题一次 + 取证一次 + 三平台适配预判 | 一题三平台角度可对比；每条断言带原始出处；无出处断言=0 | 我 |
| N3 | 母版叙事 + 三形态成稿 | 三份产物论点一致；子形态新增论点=0 | 我 |
| **N4** | **60 秒样片（风险闸）** | ①不像幻灯片 ②静帧时长与节奏达标 ③成本落在预估区间 | **你**（看 3 分钟给结论） |

### 12.4 那我以后怎么跟你承诺进度
不用"工期"，用三条：
1. **节点完成即报**：每完成一个节点给你一张卡，不用你追问；
2. **卡住就报**：某个节点超过约定时间没动静（比如 2 小时无进展，或等你超过 6 小时），我主动说"卡在 X，需要你 Y"；
3. **不跨节点承诺日期**：我可以说"下一个节点是 N4 样片"，但不承诺"周三给你"——因为我的一轮可能 20 分钟也可能 2 小时，硬报日期等于骗你。

**一句话**：把"18–20 个工作日"作废。正确的说法是"**12 个节点，其中 3 个卡在你手上、2 个卡在平台和自然时间上，其余在我手上**"。
